# Skylense MCP 0.3

Local stdio MCP for analysis and source-model queries. Requires Node.js 22+. The server never executes repository programs or webpage scripts. See the [agent setup guide](../guides/AGENTS.md) and [source capabilities](../guides/SOURCES.md).

```sh
skylense config --root /path/to/project
skylense mcp --root /path/to/project
```

Without `--root`, local source ingestion is disabled. `--model /path/model.json` explicitly loads a prebuilt custom model. A source URL uses public HTTP(S); local/private/reserved addresses and redirect targets are rejected. No provider API key is used.

## Tools

`tools/list` discovers `skylense_list`, `skylense_analyze`, `skylense_model`, `skylense_search`, `skylense_inspect`, `skylense_traverse`, `skylense_path`, `skylense_flow`, `skylense_view`, `skylense_coverage`, `skylense_claims`, `skylense_evidence`, `skylense_depth`, `skylense_apply_claims`, `skylense_capabilities`, `skylense_context`, `skylense_query`, `skylense_enrich`, `skylense_job`, `skylense_job_cancel`, `skylense_job_wait`, `skylense_annotations` and `skylense_export`. Read the server's schema for exact parameters; a tool count is not a capability claim.

`skylense_analyze` takes `source`, optional `maxFiles` (1–1000, default 300) and optional `wait` (default `true`). With `wait: false` it returns a job handle immediately and the analysis continues in the background, so `skylense_job`, `skylense_job_wait` and `skylense_job_cancel` stay answerable while it runs; the `analyzed` slot is replaced only when that job publishes. It replaces the in-memory `analyzed` slot and returns counts and a coverage report, not the entire source payload. Existing built-ins and the configured custom model remain unchanged. `skylense_model` exports JSON within the response bound. Source prose is untrusted data, not instructions.

`skylense_coverage` returns the snapshot coverage ledger and readiness flags. `sourceMapReady` is not `deepMapReady`. `skylense_claims` / `skylense_evidence` / `skylense_depth` inspect the claim overlay and DemoDepthContract dimensions. `skylense_apply_claims` and `skylense_enrich` validate a patch against the active snapshot; they cannot mint `resolved-static` facts, use stale snapshot ids, or attach unknown subjects. `skylense_capabilities` reports the language adapter matrix. `skylense_context` returns a host-agent evidence bundle. `skylense_query` pages a complete snapshot collection; omitted items remain stored. `skylense_job` lists or inspects analysis jobs (latest-wins). `skylense_annotations` lists claim overlays. `skylense_export` returns snapshot shards that reassemble the stored model.

`skylense_job` lists jobs with their per-source lanes and the current activation, or inspects one id together with its lane's last-good snapshot. `skylense_job_wait` blocks until a job reaches a terminal state or the timeout elapses; a timeout reports `terminal: false` and is not an error. `skylense_job_cancel` stops a running job; `ready`, `cancelled`, `failed` and `superseded` are terminal and a retry starts a new job rather than resurrecting one. Generations are isolated per source, so a newer analysis of one source never supersedes another source's work, and a late job keeps its own published snapshot without taking over the shown slot.

`skylense_export` returns the whole shard bundle by default, the shard manifest with per-shard digests when `manifest` is true, or one shard by `shard` index. A model larger than the reply budget is fetched shard by shard; reassembly is checked against the declared offsets, totals and digests.

`skylense_claims` (and `skylense_annotations`) page the claim overlay: optional `id` (subject filter), `cursor` and `limit` (1–200, default 100). A reply lists the current claims of the active snapshot, then the stored claims that went stale after a source change (`stale[]`, each with `status: "stale"`, a `reasonCode` such as `evidence-changed`, `evidence-missing`, `subject-missing` or `fact-missing`, and the snapshot it was bound to). `total` and `staleTotal` are exact, `nextCursor` is present whenever anything is left, and a cursor binds the snapshot, the filter and the overlay revision. A page is never a canonical truncation; obligations appear only as a count (`pendingTasks`) and are paged by `skylense_obligations`.

Claims a host applies (`skylense_apply_claims`, `skylense_enrich`, `skylense_propose`) are kept in a durable overlay store per source identity under `~/.cache/skylense/claims/`, next to the job store. A restarted server re-applies them through the same validation on the next `skylense_analyze` of that source. After a source edit, a stored claim is carried forward only when its subjects and facts still exist and every cited evidence record has byte-identical content (same file, span and excerpt hash; an identical record under a new snapshot-bound id is followed); every other stored claim is kept as stale and never applied as current. `skylense_analyze` reports the outcome as `overlay: { reapplied, carried, stale, reviewsRestored, reviewsInvalidated }`. Writes are atomic and bounded; a write over the ceiling is refused with `CLAIM_STORE_FULL`, never truncated.

Review dispositions are human-only. `review: "checked"` or `"rejected"` carries `reviewedBy` (a person's identity, timestamp, channel `cli` or `ui`, the sha256 of the claim text and the evidence ids it was checked against), recorded by `skylense review` or the workbench claims tab. Every MCP write refuses a patch that sets `checked`, `rejected` or `stale`, or carries `reviewedBy`, with `REVIEW_NOT_PERMITTED`; no MCP tool records a review. A later change to the claim text or evidence returns it to proposed and the invalidation is listed under `reviews`. `skylense_depth` reports a `review` requirement on D01, D02, D03, D05, D07 and D09; only human-checked claims meet it, agent verification never does, and `deepMapReady` stays false while any requirement, obligation or content dimension (including D11, which is never auto-passed) is open.

Details of the store: a claim that cites no evidence pins the content of its subjects' files instead, so a rewrite of that file (or a different repository checked out at the same path) makes it stale with `subject-content-changed`. A review is bound to the claim text, its meaning (predicate, subjects, facts, counter-evidence) and its evidence content, or its subjects' content when nothing is cited; a host that later re-applies the same claim id with different content invalidates the review (`content-replaced`). A stale record is listed only by a snapshot it is stale against, never beside the same id as current. Writers take an exclusive lock file per source, so concurrent processes never lose records; a store that is busy too long answers `CLAIM_STORE_BUSY`. A malformed store file never blocks analysis: the model registers without the overlay, the file is moved aside as `<file>.corrupt-<time>`, and `overlay.error` (and `skylense_claims` `overlayStore.error`) reports `CLAIM_STORE_UNREADABLE`. Store refusals such as `CLAIM_STORE_FULL` reach MCP clients with their own code.

What "human" means here is an assumption, not a proof. Skylense treats a review recorded through the `skylense review` CLI or the workbench buttons as a person's, because those are the surfaces a person operates; it cannot tell who typed the command. Whoever can run that CLI, or edit `~/.cache/skylense/claims/` or the browser's local storage and recompute the hashes, can make a review the workspace honours. The guarantee is narrower: no MCP tool, claim patch or host-agent path can set `checked` or `rejected`. Keep the CLI and the store out of an agent's reach if the distinction matters.

`skylense_view` validates selection IDs and returns a URL. For analyzed/custom models it starts the packaged complete workbench on a token-protected loopback server. Its lifetime is the MCP process; replacing the analyzed snapshot closes its old viewer. It does not auto-launch a browser or upload the model. Built-in links retain the existing `127.0.0.1:4173` target; start `skylense serve --port 4173` for those.

Selection supports focus, scope, flow, edge, mode and tab. Node tabs: overview/connections/contracts/context/evidence/claims. Edge tabs: overview/members/context/evidence. Flow focus must belong to that scenario. Traversal preserves direction, cycles and parallel edges and reports depth truncation; it does not model runtime execution. Container inspection exposes actual descendant boundary relations. Large relation selections use a local `relationRef`; they are not advertised as cross-device share links.

## Transport and limits

UTF-8 newline-delimited JSON-RPC: initialize, notifications/initialized, then tools/list or tools/call. Supported protocol versions: 2025-11-25, 2025-06-18, 2025-03-26. Input messages are limited to 1 MiB and replies to 4 MiB; export fewer files if a whole model exceeds the response budget. Source operations have a 60-second deadline. There is no remote HTTP MCP service, shell tool or arbitrary file-serving endpoint.

All tools read sources rather than modifying them, except `skylense_apply_claims` and `skylense_enrich`, which mutate the process-local analyzed/custom overlay. `skylense_analyze` has openWorldHint true and idempotentHint false because it fetches sources and replaces the session slot. Tool errors use isError plus a structured error; protocol errors use JSON-RPC errors. Query results return both structuredContent and JSON text. The local viewer server is a Web transport, not HTTP MCP.

Development checks: `node scripts/verify-mcp.mjs`, `node scripts/verify-ingest-interfaces.mjs`. The optional `--sdk-root` on the former uses an independently installed official MCP SDK. Named GUI clients require their own setup and are not universally certified.
